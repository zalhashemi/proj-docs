# How the `project-docs` skill is built

This guide explains how the `project-docs` Claude Code skill in this repository works, why
it is shaped the way it is, and how to develop it further. The skill's
[README](skills/project-docs/README.md) covers installing and using it. A PDF of the
template-based Developer pack, generated by the skill itself, is in
[`docs/pdf/developer.pdf`](docs/pdf/developer.pdf).

---

## 1. What a Claude Code skill is

A skill is a folder containing a `SKILL.md` file. Claude Code discovers skills in these places:

| Location | Scope |
|---|---|
| `.claude/skills/<name>/SKILL.md` | One project |
| `~/.claude/skills/<name>/SKILL.md` | All your projects |
| `<plugin>/skills/<name>/SKILL.md` | Wherever the plugin is enabled (**how this repo ships it**) |

This repository is both a **plugin** (`.claude-plugin/plugin.json`, skill in `skills/project-docs/`)
and a **marketplace** (`.claude-plugin/marketplace.json`, `"source": "./"`). That's why
`/plugin marketplace add zalhashemi/proj-docs` followed by `/plugin install project-docs@proj-docs` works.
Check both manifests with `claude plugin validate --strict .`.

`SKILL.md` starts with YAML front matter. Two fields matter most:

- **`description`**: what the skill does and when to use it. It is the **only** part Claude
  always sees, and it decides whether the skill triggers. That's why it lists concrete phrases
  ("docs pack", "runbook", "1-year forecast", "generate PDFs for this project") and says when
  *not* to use the skill (single README edits, code comments).
- **`when_to_use`**: extra trigger phrases. Together with `description` it is capped at 1,536 characters.

The skill's own scripts are referenced as `${CLAUDE_SKILL_DIR}/scripts/...`, so they work from
any working directory.

### Progressive disclosure: three levels

Skills load in layers, so that 37 templates and 3 reference docs cost almost nothing until they're needed:

| Level | What loads | When | Here |
|---|---|---|---|
| 1 | `name` + `description` | Always | about 1.3k characters |
| 2 | `SKILL.md` body | When the skill triggers | 150 lines: the workflow only |
| 3 | Bundled files | When a step needs them | `reference/*.md`, one template, one catalog entry |
| – | Scripts | Executed, never read | `scripts/*.py` (about 3,000 lines that never enter context) |

That's the main design rule of this skill: **anything deterministic goes into a script, and
anything Claude only sometimes needs goes into `reference/`**. The `SKILL.md` body is just the
order of steps.

## 2. Architecture

```text
                      ┌──────────────────── docs/.project-docs/ ────────────────────┐
 repo ─► scan_project.py ─► scan.json      detect_theme.py ─► theme.json     inputs.yaml (user answers)
                │                               │                                  │
                ▼                               ▼                                  ▼
      Claude drafts docs/<pack>.md  ◄── templates/<id>.md per chapter + catalog.yaml + reference/writing-standards.md
                │                    ◄── finance.py (forecast/budget tables + charts; Claude never does maths)
                ▼
         state.py record ─► state.json   …later…   state.py diff ─► patch only affected chapter sections
                │
     on request: build_pdf.py ─► docs/pdf/<pack>.pdf ─► verify_pdf.py ─► preview PNGs
```

| Component | Responsibility | Notes |
|---|---|---|
| `scan_project.py` | Repo facts → `scan.json` | Stdlib-first; honours `.gitignore`; never reads env values |
| `detect_theme.py` | Brand → `theme.json` | Tailwind v3/v4, CSS vars/shadcn, MUI etc., Flutter, Android, iOS, logo colour; WCAG fixes |
| `catalog.yaml` | Registry of 6 packs and 37 chapter types | Each chapter has one `pack`; `needs` gates it on evidence; `scan_keys` ties it to the scan facts it depends on |
| `templates/` | Outline per chapter type | `<!-- guide: -->` comments are stripped at render time |
| `finance.py` | Forecast and budget maths | Inputs → formulas → outputs; unknown inputs become marked assumptions |
| `build_pdf.py` + `assets/` | Markdown → HTML → PDF | WeasyPrint by default, Chromium as fallback; CSS variables from the theme; design rules in `DESIGN.md` |
| `verify_pdf.py` | Quality gate | Blank pages, margin overflow, fonts, TOC/links, contrast; thumbnails |
| `state.py` | Lifecycle, chapter selection and incremental updates | Stage, `packs` (chapters with evidence), per-pack hashes, per-chapter change summaries, hand-edit detection |
| `preview_themes.py` | Compare themes | One swatch page per theme |

## 3. Key design decisions

### 3.1 One Markdown pack per category; PDFs only on request
Each run writes one `docs/<pack>.md` per pack you pick, never one file per document type. Every
chapter type belongs to exactly one pack, so nothing is written twice, and `state.py packs`
leaves out chapters the scan can't back up (a `needs` key with no evidence). A pack ends with a
single assumptions chapter that names what was left out and why. Nothing is rendered unless you
ask, and then only the packs you name.

### 3.2 Planning pack first, everything else when the project is complete
A project that doesn't exist yet can't have a runbook. `state.json` records a **stage**:
`planning` allows only the Planning pack (the build plan), and `complete` unlocks the others. `scan_project.py`
suggests a stage (two or fewer code files and fewer than 10 commits counts as planning), and
Claude confirms it with you. An explicit request for a specific pack works in any stage.

### 3.3 Updates patch; they never rewrite
When the code changes, `state.py diff` compares the stored scan snapshot with a fresh scan,
but only on the `scan_keys` of each pack's chapters. Adding one route flags **only** the
Developer pack's `api-reference` chapter, with "route PATCH /orders/{order_id} added", and
offers chapters that were left out but now have evidence. Claude then edits just the section
that covers that fact, runs `state.py bump` (1.0.0 → 1.0.1), and re-renders the PDF only if
one already exists. If you edited the
Markdown yourself, its hash no longer matches, so Claude shows the patch as a diff and waits
for approval. Nothing runs in the background; updates happen only when you ask.

### 3.4 Never fabricate
`reference/writing-standards.md` is the contract. Anything the repo doesn't show and you didn't
say becomes `> [!ASSUMPTION]` or `⟨assumption⟩`. Both render as a dashed amber callout or tag,
and every pack ends with an assumptions chapter. Commands that weren't run are tagged
`⟨untested⟩`. Finance numbers come only from `finance.py`. Legal-adjacent docs carry a
"not legal advice" line and never say "compliant".

### 3.5 Rendering
- **WeasyPrint is the default** (proper paged-media CSS, `target-counter()` for TOC page
  numbers). This Mac has no Pango, so the code falls back to **Chromium through Playwright**,
  using the installed Chrome. The fallback is automatic and reported in the JSON output.
- **Chromium has no `target-counter()`**, so `build_pdf.py` renders twice. Pass 1 includes
  invisible TOC markers. PyMuPDF reads the destination page of each TOC link, and pass 2
  prints those numbers. The TOC keeps its size between passes, so pages don't move.
- **`base.css` uses only CSS variables.** `@page` rules (size, running footer, a named page
  per chapter) are generated in Python, because margin boxes need literal strings.
- **The chapter band is drawn with page margin boxes.** Each chapter page gets a 58mm left
  margin whose margin boxes are painted in the pack colour and hold the number, title, pack and
  project. Chromium clips page content to the content box, so nothing in the flow can bleed to
  the edge, and a floated full-height column pushed tables off the page. Margin boxes paint only
  when they have content, and they overlap by 1pt so viewers show no seams.
- **Chromium merges margin-box text into matching bookmarks** ("ContentsContents"), so
  post-processing collapses doubled outline titles.
- **Post-processing in PyMuPDF** sets metadata and rewrites cross-document links as relative
  "go to file" links, so a folder of PDFs still works after it's moved.

### 3.6 Ponytail: the smallest complete solution
The skill was built in "lazy senior developer" mode: every requirement ships, with the least
code that does the job.
- One shared helper module (`_common.py`). No plugin systems, no config layers.
- Mermaid diagrams use `mmdc` if installed; there's no bundled mermaid.js.
- Fonts were downloaded once at build time; nothing touches the network at runtime.
- Known limits are written down rather than over-engineered (see the README's "Known limitations").

## 4. How it was built (phases)

| Phase | Delivered | Exit check |
|---|---|---|
| 1. Foundation | `SKILL.md`, `reference/`, `catalog.yaml` (37 docs), 37 templates, 5 themes, fonts, venv | Catalog/template/theme tests; Chromium smoke test |
| 2. Scan and theme | `scan_project.py`, `detect_theme.py`, 3 fixture projects | Scan and theme tests on all fixtures plus edge cases |
| 3. Render and verify | `build_pdf.py`, `base.css`, cover, `verify_pdf.py`, `finance.py`, `state.py`, `preview_themes.py` | Render, finance-maths and update-tracking tests |
| 4. End-to-end | Drafted sample docs, visual QA fixes, sample PDFs in `samples/` | Full workflow test per fixture |
| 5. Documentation | Skill README, this guide, dogfooded developer guide PDF | Full suite passing |
| 6. Open-source release | Plugin layout, `bootstrap.py`, CI on Linux/macOS/Windows, LICENSE | CI green on every renderer |
| 7. v2: packs | One Markdown pack per category, `needs`-gated chapters, PDFs on request, pack-level update tracking | Full suite passing |
| 8. v2: Spectrum design | Default theme and stylesheet from an impeccable + design-taste direction round (`PRODUCT.md`, `DESIGN.md`) | `verify_pdf.py` on every sample, pages reviewed |
| 9. v2: samples and docs | Samples and dogfood regenerated as packs | Full suite passing |

Problems found by **looking at rendered pages** in Phase 4 (and fixed):
- the chart legend overlapped bars
- key/value tables showed an empty header bar
- diagram source blocks split across pages
- JetBrains Mono ligatures turned `->` into arrows

Automated checks alone wouldn't have caught any of these.

## 5. Developing the skill

### Setup

```bash
git clone https://github.com/zalhashemi/proj-docs.git && cd proj-docs
python3 skills/project-docs/scripts/bootstrap.py --install     # venv in ~/.cache/project-docs/venv
~/.cache/project-docs/venv/bin/python -m pytest tests -q
```

To try your working copy in Claude Code, either symlink it as a personal skill
(`ln -s "$PWD/skills/project-docs" ~/.claude/skills/project-docs`) or add the clone as a local
marketplace (`/plugin marketplace add ./`).

### Repository layout

```text
proj-docs/
├── .claude-plugin/              # plugin.json + marketplace.json
├── skills/project-docs/         # THE SKILL (what users install)
│   ├── SKILL.md, catalog.yaml, README.md, requirements.txt
│   ├── reference/  templates/  themes/  assets/
│   └── scripts/                 # bootstrap.py + the 8 tools
├── tests/                       # pytest suites
│   ├── fixtures/                # fake React, FastAPI and Flutter projects
│   └── sample_docs/             # pack Markdown Claude drafted for each fixture (used by test_e2e.py)
├── samples/                     # example packs + one Developer PDF each: brightcart (React), ledgerline (FastAPI); theme-previews
├── docs/                        # the skill's output for THIS repo (dogfood)
├── .github/workflows/ci.yml     # tests on Linux (WeasyPrint + Chromium), macOS, Windows
├── DEV_GUIDE.md  CONTRIBUTING.md  CHANGELOG.md  LICENSE  README.md
├── PRODUCT.md  DESIGN.md        # product context and the default look's design system
├── .impeccable/                 # direction round sketches, review captures, design.json
```

### Common tasks

| Task | How |
|---|---|
| Add a chapter type | Catalog entry (with its `pack`) + template; see the README section "Add a chapter type" |
| Add a theme | `themes/<name>.json`; see the README section "Add a theme" |
| Teach the scanner a new framework | Add it to `FRAMEWORKS` (and `FRONTEND`/`BACKEND`/…) in `scan_project.py`, then add a fixture assertion in `test_scan.py` |
| Support a new theme source | Add an extractor in `detect_theme.py` → `build_theme()`, then a case in `test_theme.py` |
| Change the look of the PDFs | `assets/base.css` (variables only), `assets/cover.html.j2`, or `page_css()` in `build_pdf.py` for the chapter band; follow `DESIGN.md`, re-render a sample and look at it |

### Debugging a rendering problem

```bash
PY=~/.cache/project-docs/venv/bin/python
$PY skills/project-docs/scripts/build_pdf.py samples/brightcart/docs/developer.md
$PY skills/project-docs/scripts/verify_pdf.py samples/brightcart/docs/pdf/developer.pdf --dpi 80
open samples/brightcart/docs/.project-docs/preview/developer-p03.png
```

`build_pdf.py` prints warnings (renderer fallback, Mermaid not rendered, unfilled
`{{placeholders}}`, missing logo) in its JSON output. Read them first.

### Releasing

1. Bump `version` in `.claude-plugin/plugin.json` and add the section to `CHANGELOG.md`
   (`test_plugin_manifests` enforces that they match).
2. Make sure CI is green, then tag: `git tag v2.0.1 && git push --tags`.
3. Users get the update with `/plugin marketplace update proj-docs`.
